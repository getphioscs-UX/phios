# 5. `definition`

**Continuation Qualification** 是 Navigation 对“当前路径是否仍然有资格继续占据默认位置”进行正式判断的机制。

它不问：

> “系统是不是还没有崩溃？”

而是问：

> **“当前路径虽然仍然能够运行，但它是否仍然足够适配现实，以至于继续保持原方向仍然合理？”**

因此，必须区分：

```
STILL_RUNNING
```

与：

```
STILL_QUALIFIED_TO_CONTINUE
```

两者不是同一件事。

一个人可以继续完成工作；

一家企业可以继续交付；

一段关系可以继续维持；

一个家庭可以继续按照旧方式运转；

但这些事实只能证明：

```
FUNCTION_PERSISTS
```

不能自动证明：

```
DIRECTION_REMAINS_QUALIFIED
```

因此：

> **NAV-11 的核心不是判断系统有没有停止，而是判断“继续”是否仍然值得拥有默认资格。**

---

# 6. `navigationMeaning`

现实中的惯性会给当前路径一种特殊优势：

```
已经这样做
→ 不需要解释

想改变
→ 必须解释
```

Navigation 必须取消这种不对称。

正确结构应是：

```
CONTINUE
```

与：

```
ADJUST
PREPARE
PAUSE
CHANGE
EXIT
```

一样，都必须拥有现实依据。

这并不意味着每一次都重新审判现状，而是：

> **当 NAV-09 已经识别出具有决策意义的变化以后，原方向必须重新取得继续资格。**

因此 NAV-11 是：

```
Decision-Relevant Change
↓
Current Path Still Running
↓
Does Running Still Justify Continuing?
↓
Continuation Qualification
```

# 10. Core Continuation States

建议 runtime 至少区分：

```
CONTINUATION_QUALIFIED
CONTINUATION_QUALIFIED_WITH_MONITORING
CONTINUATION_QUESTIONED
CONTINUATION_REQUIRES_REASSESSMENT
CONTINUATION_NOT_QUALIFIED_BY_CURRENT_EVIDENCE
CONTINUATION_BASIS_UNKNOWN
```

---

## A. `CONTINUATION_QUALIFIED`

当前路径仍然：

```
produces intended value
cost remains acceptable
capacity remains adequate
future options remain sufficiently preserved
```

因此继续仍有现实依据。

---

## B. `CONTINUATION_QUALIFIED_WITH_MONITORING`

当前仍可继续，但某些条件已经接近边界。

例如：

```
cost rising
capacity narrowing
external condition changing
```

因此：

```
continue
+
monitor
```

更合理。

---

## C. `CONTINUATION_QUESTIONED`

当前路径仍在运行，但继续资格已经不能仅靠惯性维持。

例如：

```
result stable
but cost materially rising
```

---

## D. `CONTINUATION_REQUIRES_REASSESSMENT`

变化已经触及：

```
core decision basis
```

当前路径必须与其他方案重新比较。

---

## E. `CONTINUATION_NOT_QUALIFIED_BY_CURRENT_EVIDENCE`

现有证据无法继续支持：

```
keep current direction as default
```

注意：

这不等于：

```
must stop immediately
```

而是：

```
current path loses automatic priority
```

# 12. `allowedInference`

NAV-11 可以：

## A. 识别“还能做”与“仍值得这样做”不同

例如：

```
employee still delivers
```

只能证明：

```
delivery remains possible
```

不能自动证明：

```
current workload is still appropriate
```

---

## B. 识别结果没变但交换关系已变

例如：

```
salary unchanged
```

但：

```
hours increased
recovery decreased
family cost increased
```

则继续资格需要重审。

---

## C. 识别一个路径正在缩小自己的评价标准

例如：

过去评价：

```
income
growth
health
family
```

后来只剩：

```
income
```

系统可以提示：

```
EVALUATION_SCOPE_NARROWING
```

---

## D. 识别过去成功不等于当前资格

例如：

```
this business model worked for 10 years
```

只能证明历史适配。

---

## E. 识别继续路径是否仍保留未来选项

如果继续当前方向会：

```
lock location
increase debt
reduce skill mobility
```

则必须进入 continuation qualification。

---

# 13. `forbiddenInference`

NAV-11 严禁：

## A. 把“没有失败”当成继续充分证据

禁止：

```
not collapsed
→ continue qualified
```

---

## B. 把长期存在当成正确证明

禁止：

```
we have always done this
→ still best
```

---

## C. 把过去投入变成未来义务

禁止：

```
already spent years
→ must continue
```

---

## D. 用 symbolic method 证明现方向应该继续

禁止：

```
BaZi says stable
→ continuation qualified
```

---

## E. 因为当前结果还在，就忽略代价转移

例如：

```
family still functioning
```

不能忽略：

```
one person carrying most hidden burden
```

---

## F. 把“继续资格不足”直接写成“立即停止”

资格不足只触发：

```
REASSESSMENT
```

不是自动 exit。

# 14. `decisionEffect`

NAV-11 主要影响：

```
OPTION_WEIGHT
DEFAULT_PATH_PRIORITY
WAIT_ACT_BALANCE
REASSESSMENT_REQUIREMENT
STRUCTURAL_CHANGE_ADMISSION
```

其核心 effect 是：

```
DEFAULT_PATH_PRIORITY
```

也就是：

> **当前路径还能不能继续享有“默认先保持”的特权。**

---

# 15. `decisionThresholdEffect`

如果当前路径：

```
CONTINUATION_QUALIFIED
```

则不需要因为存在变化就提高行动强度。

如果：

```
CONTINUATION_REQUIRES_REASSESSMENT
```

则后续 options 应重新比较。

如果：

```
CONTINUATION_NOT_QUALIFIED_BY_CURRENT_EVIDENCE
```

则继续本身也需要被当成一个普通候选路径重新评估。

但这不意味着：

```
change threshold automatically lowered
```

---

# 16. `authorityBoundary`

NAV-11 可以：

- 判断继续资格；
- 取消默认优先权；
- 标记需要重审；
- 暴露当前路径的真实交换关系；
- 比较继续所保存与失去的东西。

NAV-11 不可以：

- 因继续资格下降而自动改变方向；
- 因系统仍运行而宣称健康；
- 把过去成功外推到未来；
- 用 symbolic interpretation 保证延续；
- 替用户决定何时结束。

---

# 17. `humanDecisionBoundary`

即使系统判断：

```
CONTINUATION_NOT_QUALIFIED_BY_CURRENT_EVIDENCE
```

用户仍然可以选择：

```
continue temporarily
```

但 Navigation 应明确显示：

```
why continuation no longer has default support
what cost is being accepted
what should be monitored
when to reopen
```

不能把用户继续选择标记成：

```
incorrect
```

# 28. Function vs Qualification Rule

冻结：

```
FUNCTION
≠
QUALIFICATION
```

例如：

```
system delivers
```

证明：

```
system can still deliver
```

不证明：

```
system should continue unchanged
```

# 29. Historical Success Rule

冻结：

> **Past success can support confidence in a path, but it cannot renew that path’s qualification without current reality support.**

中文：

> **过去的成功可以增加对一条路径的理解与信任，却不能在缺少当前现实支持时自动续期它的继续资格。**

```

```

# 31. Evaluation Scope Rule

如果当前路径只有在不断删除原有评价标准后才能被称为“成功”，必须标记：

```

```

例如从：

```
income + health + family + growth
```

逐渐缩成：

```

```

这必须进入 continuation review。

# 32. Hidden Subsidy Rule

如果系统表面结果不变，是因为有人或某部分不断补贴：

```
extra unpaid time
health cost
family sacrifice
cash reserves
employee overwork
```

应标记：

```
HIDDEN_CONTINUATION_SUBSIDY
```

这会交给 NAV-12 进一步处理。

```

```

```

# 39. Canonical Qualification Rule

> **A path remains qualified only when its current value, cost, capacity demands, responsibility structure, and future-option effects remain sufficiently acceptable under current reality.**

中文：

> **一条路径只有在当前现实中，其价值、成本、容量要求、责任结构与未来选择影响仍然足够可接受时，才继续拥有现实资格。**

---

# 40. Canonical Default Rule

> **Continuation is a decision, not a neutral default, once material reality has changed.**

中文：

> **一旦现实发生了具有决策意义的变化，继续本身就是一个决定，而不再是中立默认。**

---

# 41. Canonical Review Rule

> **Loss of default qualification requires reassessment, not automatic abandonment.**

中文：

> **失去默认继续资格意味着必须重新比较，而不是自动放弃。**

# 5. `definition`

**Maintenance Cost** 是 Navigation 对“为了让当前结果继续存在，系统实际正在支付什么”进行正式识别与比较的机制。

它不只是金钱成本，也不等同 Book III 中对 maintenance、runtime accumulation 或 degradation 的解释。

NAV-12 不重新回答：

> 为什么系统需要维护？  
> 为什么负荷会累积？  
> 为什么恢复会失败？

这些属于前册已经建立的运行机制。

NAV-12 只问：

> **既然当前路径仍然能够维持，它现在需要支付的真实代价，是否已经改变了继续这个选择的资格？**

例如：

```
结果：
收入仍然 RM10,000 / month
```

但为了维持同一收入，现在需要：

```
过去：45 hours / week
现在：65 hours / week
```

那么不能简单写成：

```
result unchanged
→ decision unchanged
```

因为真正变化的是：

```
exchange structure
```

同样：

```
company revenue unchanged
```

但如果维持它已经依赖：

```
discounting
staff overtime
deferred maintenance
cash reserve drawdown
```

那么当前路线的现实含义已经改变。

因此：

> **NAV-12 把“结果是多少”与“为了让这个结果继续存在，系统正在付出什么”重新放回同一个决定。**

---

# 6. `navigationMeaning`

很多系统不是先失去结果，而是先让结果变得越来越昂贵。

这正是 Navigation 最容易迟到的地方。

如果系统只观察：

```
output
income
delivery
relationship status
business survival
```

就可能忽略：

```
time cost
financial subsidy
capacity depletion
relationship burden
recovery loss
future-option loss
responsibility concentration
```

于是表面上：

```
nothing changed
```

实际上：

```
everything required to keep it unchanged has changed
```

NAV-12 的作用因此是：

```
Continuation Qualification
↓
Identify Maintenance Inputs
↓
Compare Present Cost with Prior Cost
↓
Assess Whether Exchange Still Qualifies
```

# 5. `definition`

**Default Direction Loss** 是 Navigation 对“原本持续中的方向何时不应再被当成默认答案”进行正式判断的机制。

它不是：

```
CURRENT PATH FAILED
```

也不是：

```
CHANGE NOW
```

更不是：

```
PAST DECISION WAS WRONG
```

它真正判断的是：

> **当前方向是否仍然可以只因为“已经这样走了一段时间”，就继续享有不需要重新比较的优先权。**

现实中的很多路径一开始都有充分理由。

例如：

```
选择某份工作
进入某个行业
维持某种家庭安排
采用某种商业模式
居住在某个地方
持续一项长期投资
```

当初可能完全合理。

问题在于，随着现实变化，人很容易把：

```
当时有理由选择
```

悄悄转换成：

```
现在仍有理由继续
```

这两个命题并不等价。

因此：

> **NAV-13 不负责证明新方向更好，而是判断旧方向是否已经失去“默认延续”的特权。**

---

# 6. `navigationMeaning`

在没有 Navigation 的情况下，现实通常存在一种强烈的不对称：

```
继续现状
→ 不需要解释

改变现状
→ 必须证明
```

这种结构会让惯性本身变成隐藏权威。

NAV-13 要做的是重新建立对称：

```
CONTINUE
ADJUST
WAIT
PREPARE
CHANGE
EXIT
```

都只是候选路径。

当旧方向赖以成立的条件已经改变以后：

```
CONTINUE
```

也必须重新回答：

> 为什么现在还值得继续？

因此 NAV-13 建立：

```
Continuation Qualification
+
Maintenance Cost
+
Decision-Relevant Change
↓
Does Current Direction Still Deserve Default Priority?
```

**Canonical Question｜规范问题**

> **当一个问题开始跨越多个生活领域以后，为什么它不能再只被当成原来的局部问题处理？**

```

```

```

```

## 3. `canonicalTitleEn`

```
Cross-Domain Propagation
```

## 4. `canonicalQuestion`

```
当一个问题开始跨越多个生活领域以后，

```

---

# 5. `definition`

**Cross-Domain Propagation** 是 Navigation 对“原本发生在一个领域中的变化，是否已经开始影响其他现实领域”进行正式识别与判断的机制。

它不是简单计算：

```
affectedDomains = 3
```

也不是：

```
领域越多
→ 问题一定越严重
```

它真正要回答的是：

> **一个原本局部的问题，是否已经开始改变其他领域的运行条件，以至于原来的局部处理方式已经不足以覆盖它真正产生的现实影响？**

例如，一个问题最初可能只是：

```
WORK
```

表现为：

```
工时增加
```

如果随后开始出现：

```
工作时间增加
→ 恢复时间减少

恢复时间减少
→ 家庭互动质量下降

家庭安排恶化
→ 外包照护支出增加

支出增加
→ 财务缓冲下降
```

那么当前问题已经不能只写成：

```
workload issue
```

因为它已经形成：

```
WORK
→ CAPACITY
→ RELATIONSHIP / FAMILY
→ FINANCIAL
```

的现实传播。

因此：

> **NAV-14 的核心不是统计受影响领域，而是判断一个变化是否已经从局部条件转变成跨领域现实约束。**

---

# 6. `navigationMeaning`

一个问题尚未扩散时，局部回应通常拥有较高资格。

例如：

```
工作安排不合理
```

可能通过：

```
重新排程
减少会议
重新分工
```

得到改善。

但如果同一问题已经持续影响：

```
income
health capacity
family coordination
location
future career options
```

那么 Navigation 需要重新判断：

> 我们现在究竟还在修一个局部参数，还是一个原本局部的问题已经开始改变整个 Decision Space？

这就是 NAV-14 的作用：

```
Local Change
↓
Propagation Mapping
↓
Cross-Domain Consequence
↓
Priority Reassessment
```

因此，跨领域扩散的真正意义不是：

```
more domains = more urgency
```

而是：

```
more domains
may change
what must be protected first
```

# 10. Core Propagation States

建议 runtime 至少区分：

```
NO_PROPAGATION_ESTABLISHED
LOCAL_SPILLOVER
MULTI_DOMAIN_PROPAGATION
SYSTEMIC_PROPAGATION
PROPAGATION_UNCONFIRMED
PROPAGATION_RELATION_UNKNOWN
```

---

## A. `NO_PROPAGATION_ESTABLISHED`

问题目前仍然：

```
contained
local
```

没有足够证据说明它已经改变其他领域。

---

## B. `LOCAL_SPILLOVER`

一个局部问题开始轻度影响邻近领域。

例如：

```
workload
→ less family time
```

但其他系统条件仍稳定。

---

## C. `MULTI_DOMAIN_PROPAGATION`

一个问题已经实质影响两个或以上重要领域。

例如：

```
work
→ recovery
→ family
→ finance
```

此时需要重新评估回应层级。

---

## D. `SYSTEMIC_PROPAGATION`

问题不再只是跨几个领域，而开始改变整体生活结构。

例如：

```
job instability
→ income instability
→ housing viability
→ child schooling
→ location choice
```

此时原 Decision Object 甚至可能需要重新打开。

---

## E. `PROPAGATION_UNCONFIRMED`

系统怀疑存在扩散，但证据不足。

---

## F. `PROPAGATION_RELATION_UNKNOWN`

多个领域同时出问题，但：

```
whether A causes B
```

尚无法确定。

---

# 11. `allowedInference`

NAV-14 可以：

## A. 识别一个条件已经产生 secondary effects

例如：

```
work hours increased
```

用户明确报告：

```
less sleep
less family time
```

可以建立：

```
SUPPORTED_PROPAGATION
```

---

## B. 识别问题正在进入更多领域

例如：

```
financial pressure
→ postponing medical care
→ relationship conflict
```

可以标记：

```
MULTI_DOMAIN_PROPAGATION
```

前提是各 link 有现实支持。

---

## C. 识别扩散使优先级发生变化

例如：

原本 Decision Object：

```
怎样提升职业成长
```

但后来：

```
job demands
→ severe financial / family / capacity constraints
```

那么当前重点可能从：

```
growth optimization
```

转为：

```
stability preservation
```

系统可以提出：

```
PRIORITY_REASSESSMENT_REQUIRED
```

但不能自行设定最终价值优先级。

---

## D. 识别 secondary effect 反过来强化原问题

例如：

```
workload
→ poor recovery
→ lower work capacity
→ more overtime
```

可以标记：

```
PROPAGATION_LOOP
```

---

## E. 识别扩散仍可被局部阻断

例如：

```
workload
→ childcare disruption
```

如果 childcare support 可以恢复，则：

```
PROPAGATION_INTERRUPTIBLE
```

可以成为后续行动候选。

---

# 12. `forbiddenInference`

NAV-14 严禁：

## A. 把相关性自动写成因果传播

禁止：

```
睡眠变差
+
财务压力增加
→ 财务压力导致睡眠变差
```

除非来源支持。

---

## B. 把领域数量当严重度分数

禁止：

```
4 domains affected
→ severity 4
```

不同领域的重要性与后果不同。

---

## C. 用 symbolic reading 建立现实传播链

禁止：

```
BaZi shows pressure in career and wealth
→ career problem spreading to finance
```

---

## D. 把一个人的问题自动投射到其他人

例如：

```
user stressed
→ partner relationship damaged
```

必须有现实 evidence。

---

## E. 把任何 secondary effect 都升级成 SYSTEMIC

局部外溢不等于结构性扩散。

---

## F. 因为扩散存在就直接建议最大改变

```
MULTI_DOMAIN_PROPAGATION
≠
STRUCTURAL_EXIT_REQUIRED
```

当影响从：

```

```

扩展到：

```

```

```

时，通常需要提高：

同时，继续维持当前路径也可能需要更高的重新证明。

原则：

> **跨领域影响越广，越不能只从原问题所在领域判断下一步。**

# 15. `authorityBoundary`

NAV-14 可以：

- 建立传播图；
- 标记 secondary effects；
- 标记 propagation loops；
- 标记跨领域影响；
- 触发 priority reassessment；
- 触发更高 response level；
- 建议其他领域需要进入 Navigation。

NAV-14 不可以：

- 在没有证据时建立因果链；
- 自动决定哪个生活领域最重要；
- 自动覆盖用户价值；
- 自动将扩散解释为失败；
- 自动升级至结构退出。

# 16. `humanDecisionBoundary`

当一个问题开始跨领域扩散时，Navigation 可以说：

> 这个问题现在已经同时影响工作、家庭与财务，因此不再适合只从工作效率来判断。

但不能直接说：

> 家庭一定应该优先于职业。

用户必须参与确认：

```
which domain cannot be sacrificed
which cost remains acceptable
which consequence matters most
```

这会为 NAV-19 Value Preservation 建立基础。

# 28. Co-Occurrence Rule

冻结：

> **Two conditions appearing together do not establish that one propagated into the other.**

中文：

> **两个条件同时出现，并不能证明其中一个传播成了另一个。**

如果因果关系未知：

```
PROPAGATION_RELATION_UNKNOWN
```

必须合法保留。

---

# 29. Scope Expansion Rule

如果原 Decision Object 是：

```
career
```

但现实影响已经扩展到：

```
family
financial
capacity
```

并不一定立刻创建三个新的 Decision Object。

系统首先应判断：

```
same decision with wider consequence scope?
```

还是：

```
multiple separate decisions now exist?
```

如果后者成立，应返回：

```
NAV-01
SPLIT_REQUIRED
```

---

# 30. Priority Reassessment Rule

传播会改变 priority，当且仅当：

```
secondary effects
materially change
what must be protected or resolved first
```

例如：

原问题：

```
career growth
```

后来发现：

```
cash runway = 1 month
```

那么短期：

```
financial continuity
```

可能需要先获得决策关注。

但这不是永久价值排序。

而是：

```
CURRENT NAVIGATION PRIORITY
```

---

# 31. Propagation Loop Rule

如果出现：

```
A → B → C → A
```

例如：

```
work overload
→ low recovery
→ lower work capacity
→ more overtime
```

应标记：

```
PROPAGATION_LOOP
```

因为此时单点调整可能不足。

但仍不自动推出 structural change。

---

# 32. Propagation Interruptibility Rule

Navigation 应识别：

```
where the chain can be interrupted
```

例如：

```
workload
→ childcare disruption
→ family conflict
```

如果增加照护支持可以阻断传播，则应保留：

```
INTERRUPTION_POINT
```

作为后续候选。

这使 Navigation 不会把：

```
origin problem
```

直接等同于：

```
must remove origin entirely
```

---

# 33. Cross-Domain Cost Rule

同一个后果不能重复计算。

例如：

```
reduced work hours
→ lower income
```

在 Financial 与 Career 两处都出现时，系统应保持同一 source lineage。

不得把它统计成两个独立损失来夸大影响。

---

# 34. Domain Priority Is Not Domain Value

冻结：

> **A domain can become the current navigation priority without becoming the most important domain in a person’s life.**

中文：

> **一个领域可以暂时成为当前 Navigation 的优先处理对象，却不代表它因此成为这个人生命中最重要的领域。**

例如：

```
urgent housing problem
```

可以暂时取得 priority，

但不代表：

```
housing > family > career
```

成为永久价值排序。

# 35. Customer Projection Example

内部：

```
Origin:
Work

Primary change:
workload +40%

Propagation:
Work → Recovery
SUPPORTED

Recovery → Family Coordination
USER_REPORTED / SUPPORTED

Family Coordination → Additional Care Cost
VERIFIED FINANCIAL

State:
MULTI_DOMAIN_PROPAGATION
```

客户可以看到：

> **这个问题现在已经不只是工作量的问题。**
> 
> 最初发生变化的是工作：工时持续上升；随后受到影响的是恢复时间，而恢复不足又开始改变家庭安排，现在额外的照护安排已经进入实际支出。也就是说，工作问题的后果已经进入家庭与财务两个领域。
> 
> 这并不自动说明你必须离开工作，但它意味着接下来不能再只问“工作还能不能撑”，而需要同时判断：当前收入值得用多少恢复、家庭协调和财务弹性去交换，以及这条传播链能不能在较小的位置被截断。

# 40. Canonical Causality Rule

> **Cross-domain co-occurrence must not be presented as propagation unless the relationship is observed, supported, or explicitly retained as uncertain.**

中文：

> **跨领域扩散可以改变当前最需要先处理什么，却不能替一个人决定生命中什么最重要。**

# 42. Canonical Containment Rule

> **When propagation can be interrupted at a smaller and more reversible point, that interruption must remain visible before the origin path is treated as requiring complete removal.**

中文：

> **当传播能够在更小、更可逆的位置被阻断时，这个阻断点必须保持可见，而不能直接把移除最初路径当成唯一答案。**

# NAV-15｜Capacity Constraint

## 容量约束｜一个方案即使很好，什么时候也已经不具备现实资格

**Canonical Question｜规范问题**

> **当一个人、家庭、组织或系统已经没有足够容量承受下一步时，为什么“理论上正确”仍然不等于“现实上可行”？**

## 4. `canonicalQuestion`

```
当一个人、家庭、组织或系统已经没有足够容量承受下一步时，
为什么“理论上正确”仍然不等于“现实上可行”？
```

---

# 5. `definition`

**Capacity Constraint** 是 Navigation 对“当前现实究竟还有多少能力承受、执行、维持并恢复某项行动”进行正式判断的机制。

它不是简单问：

> “这个方案好不好？”

也不是：

> “这个人够不够努力？”

更不是：

```
motivation
=
capacity
```

它真正回答的是：

> **当前系统是否拥有足够的现实容量，把一个候选方案从想法推进成可以承担、可以维持、可以恢复的行动？**

一个方案可能：

```
strategically sound
financially attractive
personally meaningful
long-term valuable
```

却仍然因为：

```
time unavailable
cash unavailable
attention saturated
care responsibilities high
operational bandwidth exhausted
recovery insufficient
```

而暂时不具备现实资格。

因此：

> **NAV-15 的核心不是评价方案价值，而是判断现实是否还有能力承载它。**

---

# 6. `navigationMeaning`

Navigation 如果忽略 Capacity，会形成一种危险错觉：

```
Good Option
→ Should Execute
```

但现实真正需要的是：

```
Good Option
+
Enough Capacity
→ May Become Executable
```

例如：

```
创业
```

可能长期方向正确；

但如果当前：

```
现金缓冲不足
家庭照护责任高
现职每周60小时
没有执行时间
```

那么真正的问题并不是：

> 创业值不值得。

而是：

> **当前现实有没有容量让创业成为一个可承担的选项？**

因此 NAV-15 建立：

```
Candidate Option
↓
Required Capacity
↓
Available Capacity
↓
Capacity Gap
↓
Current Eligibility
```

---

## A. `FINANCIAL_CAPACITY`

包括：

```

```

不是：

```
total asset value
```

自动等于：

```
usable capacity
```

---

## B. `TIME_CAPACITY`

回答：

> 现实中真的还有多少可以投入的新时间？

例如：

```
24 hours available
```

显然不能因为日历上存在空白，就视为可投入容量。

---

## C. `ATTENTION_CAPACITY`

某个人即使还有时间，也未必还有足够：

```
cognitive bandwidth
decision bandwidth
coordination bandwidth
```

来承担新的复杂任务。

---

## D. `OPERATIONAL_CAPACITY`

对企业、家庭或项目而言：

```
people
systems
processes
execution bandwidth
```

是否还能承担新的结构。

---

## E. `RECOVERY_CAPACITY`

当前系统是否还有足够恢复空间，使投入可以持续。

NAV-15 只消费 Book III / Current Reality 已建立的 recovery 状态，不自行诊断。

---

## F. `RELATIONAL_CAPACITY`

涉及共同生活或协作时：

```
coordination
communication
care
conflict load
```

也会成为真实 Capacity。

---

## G. `RESPONSIBILITY_CAPACITY`

当前承担的：

```
children
parents
employees
debts
clients
care obligations
```

会限制新增责任。

---

## H. `SKILL_CAPACITY`

拥有兴趣不等于拥有执行能力。

必须区分：

```
willingness
potential
current executable skill
```

---

## I. `INSTITUTIONAL_CAPACITY`

```
budget
approval
headcount
legal authority
system readiness
```

等容量边界。

## A. `CAPACITY_SUFFICIENT_WITH_BUFFER`

---

## B. `CAPACITY_SUFFICIENT`

足够执行，但缓冲有限。

---

理论可执行，但：

```
small disruption
```

可能使方案失去稳定性。

---

## D. `CAPACITY_CONSTRAINED`

某个关键维度已经限制方案规模、速度或时点。

当前缺少执行该方案所需的最低容量。

```

```

而不是：

```

```

## B. 判断方案是否需要缩小规模

```

```

不等于永久关闭。

# 15. `decisionThresholdEffect`

Capacity 不足不会让 Decision Sufficiency 自动降低。

恰恰相反：

如果方案需要：

```
near-total available capacity
```

那么现实容错率下降。

因此可能需要：

```
higher evidence
smaller action
more buffer
more contingency
```

冻结原则：

> **A plan that requires nearly all available capacity carries a different decision burden from a plan that leaves meaningful reserve.**

中文：

> **一个需要耗尽几乎全部可用容量的方案，与一个仍然保留实质缓冲的方案，承担的是不同等级的决策责任。**

---

# 16. `authorityBoundary`

NAV-15 可以：

- 识别容量；
- 识别瓶颈；
- 判断容量缺口；
- 限制 action scale；
- 标记准备需求；
- 标记需要 buffer；
- 触发 option eligibility review。

NAV-15 不可以：

- 把 Capacity Deficit 变成永久拒绝；
- 把人贴成“不够强”；
- 自动要求牺牲恢复或家庭；
- 把所有资源换算成单一分数；
- 用解释系统建立现实容量。

---

# 17. `humanDecisionBoundary`

用户可以决定：

```
愿意投入多少容量
愿意保留多少缓冲
哪些责任不能被挤压
```

但 Navigation 必须让这些交换可见。

例如：

> 这个方案目前不是绝对做不到，而是需要占用你几乎全部可支配时间，并把财务缓冲压到很低；如果你仍然选择推进，就意味着你正在接受很小的恢复与错误空间。

这是：

```
visible tradeoff
```

不是：

```
system prohibition
```

```
CAPACITY_CONTEXT
```

不能直接建立：

# 21. `financialConsumer`

Financial 是 NAV-15 的核心 producer。

可提供：

```
cash buffer
liquidity
debt headroom
monthly surplus
fixed commitments
income concentration
```

例如：

```
RM100k assets
```

不等于：

```
RM100k available capacity
```

必须区分：

```
liquid
restricted
committed
illiquid
```

# 28. Required vs Available Rule

冻结：

```
REQUIRED CAPACITY
≠
AVAILABLE CAPACITY
```

Navigation 必须显式比较两者。

不能只知道：

```
user has RM50k
```

还必须问：

```
how much is actually available for this decision?
```

---

# 29. Buffer Rule

容量判断不能只看：

```
can just barely execute
```

还要看：

```
what happens if reality deviates?
```

因此建议保留：

```
CAPACITY_BUFFER
```

包括：

```
financial buffer
time buffer
recovery buffer
operational buffer
```

---

# 30. Saturation Rule

当：

```
available capacity ≈ current commitments
```

新增方案可能进入：

```
SATURATION_RISK
```

但 NAV-15 不重新解释 saturation mechanism。

它只将其作为：

```
ACTION_SCALE_CONSTRAINT
```

---

# 31. Capacity Transfer Rule

系统不能假设一种容量可以自由替代另一种。

例如：

```
more money
```

未必能替代：

```
parental presence
sleep
legal authority
specialized skill
```

因此禁止建立一个粗糙：

```
TOTAL_CAPACITY_SCORE
```

把所有维度混成单一数字。

---

# 32. Borrowed Capacity Rule

有些方案可以依靠：

```
outsourcing
family support
professional support
credit
staff
technology
```

取得额外容量。

但必须区分：

```
OWN_CAPACITY
BORROWED_CAPACITY
DEPENDENT_CAPACITY
```

并记录：

```
cost
reliability
duration
consent
```

---

# 33. Capacity Dependency Rule

如果方案只有在某个未确认资源成立时才可执行：

例如：

```
“如果父母能帮忙照顾孩子，我就能做。”
```

则状态应是：

```
CONDITIONALLY_CAPACITY_SUFFICIENT
```

而不是：

```
CAPACITY_SUFFICIENT
```

建议可作为扩展 state 或 constraint flag。

---

# 34. Capacity Deficit Rule

冻结：

> **Capacity deficit means “not currently carryable,” not “never possible.”**

中文：

> **容量不足意味着“当前现实还承载不了”，而不是“永远不可能”。**

这与 NAV-03 的：

```
NOT_YET_OPEN
```

直接连接。

---

# 35. Action Scale Rule

当：

```
full option exceeds capacity
```

但：

```
smaller version fits
```

Navigation 可以暴露：

```
LOWER_SCALE_VARIANT
```

例如：

```
full business launch
→ weekend pilot

full degree
→ one course

full relocation
→ temporary stay
```

但不能自动把小方案设成最终选择。

---

# 36. Capacity Preservation Rule

Navigation 不只需要问：

```
Can we do this?
```

还必须问：

```
What capacity remains after doing it?
```

因此：

```
postActionCapacity
```

必须可进入后续判断。

一个行动如果执行后留下：

```
near-zero recovery margin
near-zero liquidity
no operational buffer
```

即使 technically feasible，也不等于现实上稳健。

---

# 37. Capacity and Other People Rule

如果一个方案依赖其他人：

```
partner
parent
employee
childcare provider
team
```

必须区分：

```
their capacity
their consent
their obligation
```

不能把：

```
“他们应该可以帮忙”
```

直接写成 available capacity。

---

# 38. Capacity vs Willingness Rule

冻结：

> **Willingness can justify bearing a cost; it cannot manufacture capacity that does not exist.**

中文：

> **意愿可以解释为什么一个人愿意承担某项成本，却不能凭空制造原本不存在的容量。**

---

# 39. Capacity vs Potential Rule

冻结：

> **Potential describes what may become possible; capacity describes what reality can carry now.**

中文：

> **潜力描述未来可能变得可行的东西；容量描述此刻现实真正承载得了什么。**

---

# 40. Customer Projection Example

内部：

```
Option:
Start business immediately

Required:
6 months runway
20 hours/week
operational attention
basic sales capability

Available:
2.5 months runway
5–7 hours/week
high existing care responsibility

State:
CAPACITY_DEFICIT
```

客户可以看到：

> **现在真正限制这个方向的，并不是它有没有价值，而是现实暂时还承载不了完整版本。**
> 
> 你已经拥有部分技能和明确兴趣，但目前可用于新事业的时间只有每周大约五至七小时，现金缓冲也明显低于完整启动所需要的范围，同时现有家庭责任并没有减少。这意味着“创业”并没有被关闭，只是“现在直接完整启动”暂时还没有取得现实资格；下一步如果仍想保留这个方向，更有意义的问题会变成：需要先建立哪些容量，或者是否存在一个规模更小、可逆性更高的版本。

# 44. Canonical Runtime Rule

> **Navigation must test whether reality can carry an option before treating that option as currently executable.**

中文：

> **Navigation 在把一个选项视为当前可执行以前，必须先确认现实是否真的有能力承载它。**

---

# 45. Canonical Eligibility Rule

> **An option can remain valuable while temporarily losing execution eligibility because the required capacity is not yet available.**

中文：

> **一个选项可以继续具有价值，却因为所需容量尚未形成，而暂时失去执行资格。**

---

# 46. Canonical Buffer Rule

> **Bare feasibility is not the same as usable capacity; meaningful reserve must remain visible when error, delay, or recovery would matter.**

中文：

> **勉强做得到，并不等于拥有可使用的容量；只要错误、延迟或恢复具有重要后果，必要缓冲就必须保持可见。**

---

# 47. Canonical Non-Substitution Rule

> **Money, time, recovery, skill, authority, and human support are distinct capacities and must not be silently collapsed into one interchangeable score.**

中文：

> **金钱、时间、恢复、技能、权威与他人支持属于不同容量，不能被悄悄压成一个可以互相替代的总分。**

---

# 48. Canonical Human Boundary Rule

> **A person may choose to operate close to their limits, but Navigation must not hide how little capacity remains after the choice.**

中文：

> **人可以选择靠近自己的现实极限行动，但 Navigation 不能隐藏这个选择以后究竟还剩下多少容量。**

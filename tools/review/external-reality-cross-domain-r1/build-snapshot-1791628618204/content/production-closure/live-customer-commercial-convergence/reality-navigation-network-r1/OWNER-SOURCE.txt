# W2｜建立统一的 Navigation Graph Projection Contract

这是整个工程的关键，不允许跳过。

请先审查现有 RMO、RDG、NAV、客户读取投影是否已包含适用的网络语义。

只有在缺少展示契约时，才新增一个**只读、版本化的 Graph Projection**。

它不是新的 Reality Runtime，不是新的 Navigation Decision Engine，也不是第二个证据权威。

建议候选名称：

`PHI-OS-REALITY-NAVIGATION-GRAPH-PROJECTION-v1`

Graph Projection 应支持以下对象，但对象类型与关系必须先经过现有规范核对：

**Nodes / 节点**

- 当前现实要素
- 已确认事实
- 有来源的证据
- 限制与资源
- 重要关系
- 未知条件
- 决策对象
- 已确认的位置
- 经准入的可能方向
- 已确认行动
- 实际观察和结果
- 历史版本

**Edges / 连接**

每条连接必须拥有明确的关系类型和可追溯依据。

例如：

- 已确认的关联
- 已确认的依赖
- 已确认的限制
- 有条件的可能关系
- 需要进一步确认的假设
- 经准入的路径联系
- 版本之间可验证的变化关系

不能只根据两个节点在视觉上靠近，就自动生成真实世界的联系。

不得自动将相关性解释为因果性。

不得因重复观察自动宣称结构强化。

**每个节点和连接至少需要核对：**

- 稳定对象身份
- 对象及关系类型
- 来源和来源版本
- 适用范围
- 事实、报告、用户自陈或解释性来源类别
- 资料日期与当前适用状态
- 已确认、部分确认、未知或无权访问状态
- 本人和第三方权限
- 对应 Reality / Decision 版本
- 可供客户阅读的中文和英文说明

凡是缺乏成立条件的关系，必须保持缺失或未知，不得为图形完整性补线。

Graph Projection 必须 fail closed。

禁止 Graph Renderer 自行成为证据生成器、模型推断器或行为建议权威。

# W3｜建立三种实际客户网络图

## G1 — Current Reality Network

呈现客户当前已提供并允许处理的信息。

第一层先画出：

- 客户正在面对的事情
- 有关的现实条件
- 已知限制
- 资源和责任
- 已有证据
- 明确未知

只有来源中确实存在关系时才连接节点。

网络图必须允许孤立节点存在。

不应该为了让图形漂亮而使所有节点自动相连。

用户自述必须有相应标签，不冒充独立证实的事实。

在缺乏足够资料时，仍可以显示有限的当前情况节点，并明确提示还缺少什么。

## G2 — Direction & Position Network

从已有 RMO / NAV 数据生成。

图中必须区分：

- 已确认的当前条件
- 当前位置是否成立
- 决策对象是否明确
- 可用路径是否已建立
- 重要限制和依赖
- 未满足的决策条件
- 实际经准入的可能方向
- 决策权属于谁

不得用随机 Direction A/B/C 代表已经建立的路线。

不得把输入不充分时的 Graph 视觉自动升级为导航建议。

不得为用户选择方向。

可以在客户明确点击后显示该方向的详情、来源、取舍、可逆性及未解决问题。

## G3 — Reality Evolution Network

仅使用确实存在的历史资料、版本和时间证据。

图中展示：

- 之前存在的节点与关系
- 当前存在的节点与关系
- 哪些已确认关系发生变化
- 哪些新增条件改变了可行性
- 哪些原有假设被事实修正
- 是否具有足够证据判断连接得到强化或削弱

图中连接的变化必须有版本和实际来源。

不得把两次用户提问伪装成长期观察。

不得制造缺失的历史快照。

目前现有 RMO 规范中明确禁止的持久化写入，不可因为这次绘图需要历史数据就直接启用。

需要持久化 successor 时，必须依照独立的授权和迁移门槛实施。

# W5｜网络图视觉语言与交互标准

网络图必须成为正式的 PHI OS 视觉组件。

不能只是把表格外面画一些圆圈或连接线。

## 视觉要求

- 使用节点、边、方向、路径、局部子网络和明确的关系图例。
- 正式采用 Figure 1B 的结构语法作为视觉参考。
- 颜色用于区分经过定义的类型与状态，不用于制造没有来源的强弱排名。
- 不同语义的节点要有明确区分。
- 未知节点和待验证连接要明显可辨。
- 当前焦点、背景网络及可能路径要有视觉层级。
- 不允许随机粗细连接代表未经核实的影响力。
- 不允许随机节点大小暗示重要程度。
- 不允许没有数据依据的力导向动画不断改变客户对关系的理解。

## 客户交互

至少支持：

1. 点击节点查看详情。
2. 点击连接查看关系说明与证据。
3. 高亮当前节点的一阶相邻关系。
4. 在合法数据范围内切换网络层。
5. 聚焦当前决策对象。
6. 选择候选方向以查看条件、限制与未知。
7. 查看当前图谱使用的资料版本。
8. 放大、缩小、复位视角。
9. 使用键盘操作及屏幕阅读器访问相同信息。

如果网络过大，应优先显示与客户当前问题有关的局部子图，并允许逐层展开。

**不允许直接把 30 个 NAV 模块铺成 30 个互相连接的节点，假装它们就是客户的现实网络。**

NAV 模块的状态应作为相应条件或节点的评估信息，而非取代实际现实对象。

# 最终交付原则

**PHI OS Reality Navigation 的核心，不是罗列方向，而是让客户看见自己面对的现实如何形成结构、如何产生联系、哪些联系具有足够依据、方向与位置在什么条件下能够成立，以及现实变化如何改变可选择的空间。**

Figure 1B 必须从出版概念发展为整个 Navigation 的视觉语言。

但只有真实来源和已接受运行规范能够支持的部分，才可以进入实际客户网络。

**我要看到真实、可操作、有出处、能持续升级的网络导航系统，而不是另一套大型方法说明书，也不是一张漂亮却没有现实数据的图。**

完成后保留所有有效的历史成果，提交唯一 Master Human Review，等待 HUMAN ACCEPT / REJECT。
